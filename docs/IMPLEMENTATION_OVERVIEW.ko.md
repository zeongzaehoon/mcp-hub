# MCP-Cluster 구현 정리

회사 데이터를 AI에서 조회하고, 분석 결과를 차트와 보고서로 만드는 시스템이다. **회사 단위의 멀티테넌트가 구현되어 있다.** 여러 회사가 같은 MCP 서비스를 함께 사용하되, 각 사용자는 자기 회사에서 허용한 데이터와 기능에만 접근하도록 구성했다.

사용자는 연결한 AI에 “이번 달 데이터를 정리해줘”처럼 요청한다. AI는 요청에 맞는 도구를 선택하고, MCP-Cluster가 권한 확인부터 데이터 조회, 계산, 파일 생성까지 처리한다.

> 2026년 9월 30일 작업 중인 코드를 기준으로 정리했다. 아래 예시는 사용 흐름을 설명하기 위한 것이며, 실제로 할 수 있는 작업은 연결한 데이터와 부여한 권한에 따라 달라진다.

## 1. 무엇을 할 수 있나

| 하고 싶은 일 | 구현한 기능 | 받을 수 있는 결과 |
| --- | --- | --- |
| 회사 데이터 확인 | 테이블·컬렉션 목록, 구조 확인, 조건별 조회 | 조회 결과 |
| 데이터 정리 | 필요한 열 선택, 이름 변경, 중복 제거, 빈 값 처리, 정렬 | 정리된 데이터 |
| 수치 분석 | 통계, 백분위, 그룹별 집계, 상관관계, 이상치, 시계열 계산 | 계산된 지표 |
| 차트 만들기 | 선·막대·영역·산점도·히스토그램·히트맵 등 | 차트 미리보기와 저장된 산출물 |
| 파일로 받기 | CSV·Excel 내보내기 | 파일 또는 다운로드 링크 |
| 보고서 만들기 | 설명, 지표, 표, 차트를 하나의 문서로 구성 | PDF·Word·PowerPoint |
| 지표 주기적으로 확인 | 정해진 간격으로 조회·계산하고 기준값과 비교 | 실행 이력, 기준 초과 여부 |
| 보안 점검 도구 사용 | Ethie를 통해 외부 실행 서버에 작업 전달 | 도구 실행 결과 |
| 사용자와 권한 관리 | 회사, 사용자, 서버, API 키, 접근 권한 관리 | 웹 관리 콘솔 |

데이터 정리부터 보고서 작성까지의 공통 기능은 PostgreSQL, ClickHouse, MongoDB, Hacker 서버에 들어 있다. Ethie는 보안 도구 실행을 연결하는 별도 서버다.

## 2. 사용 흐름

예를 들어, 버그바운티 담당자가 “이번 달 제보를 심각도별로 정리하고 보고서로 만들어줘”라고 요청하면 다음 순서로 처리한다.

| 순서 | 처리 내용 | 담당 |
| --- | --- | --- |
| 1 | 요청을 보고 어떤 데이터와 도구가 필요한지 선택 | AI 클라이언트 |
| 2 | 호출할 도구가 있는 서버로 요청 전달 | 게이트웨이 |
| 3 | 사용자, 회사, API 키, 서버 접근 권한 확인 | 해당 MCP 서버의 공통 인증 모듈 |
| 4 | 허용된 회사 범위에서 제보 데이터 조회 | 데이터 서버 |
| 5 | 심각도별 건수 등 필요한 수치 계산 | 분석 도구 |
| 6 | 계산 결과와 차트를 산출물로 저장 | 공통 도구·파일 저장소 |
| 7 | 저장된 산출물을 보고서에 넣고 파일 생성 | 보고서 도구 |
| 8 | 결과를 설명하고 다운로드 링크 전달 | AI 클라이언트 |

AI는 작업 순서와 설명을 맡고, 수치 계산은 서버의 분석 도구가 맡는다. 보고서의 지표·표·차트도 저장된 결과를 참조한다. 설명 문장은 별도로 작성되므로, 이 구조가 문서 전체의 사실성을 자동으로 검증한다는 뜻은 아니다.

## 3. 전체 구성

크게 보면 사용자가 쓰는 AI, 요청을 받아주는 게이트웨이, 실제 작업을 하는 MCP 서버, 운영자가 쓰는 관리 콘솔로 나뉜다.

```text
사용자의 AI 클라이언트
        ↓
MCP 게이트웨이 — 하나의 연결 주소
        ↓
PostgreSQL / ClickHouse / MongoDB / Hacker / Ethie
        ↓
회사 데이터 또는 외부 보안 도구 실행 서버

관리 콘솔 → 관리 API → 회사·사용자·권한 저장 및 동기화
MCP 서버 → 권한 확인 / 접근 로그 기록 / 결과 파일 저장
```

| 구성 요소 | 하는 일 | 사용 기술 |
| --- | --- | --- |
| 관리 콘솔 | 회사와 사용자를 등록하고 권한·키·로그 관리 | React, TypeScript |
| 관리 API | 관리 정보 저장, 권한 변경 반영, 로그 적재 | FastAPI |
| 게이트웨이 | 여러 MCP 서버를 하나의 주소로 연결 | FastMCP |
| MCP 서버 | 데이터 종류에 맞게 조회·변경·분석 도구 제공 | Python, FastMCP |
| 분석 모듈 | 통계 계산, 마스킹, 해시 처리 | Rust, PyO3 |
| 관리 정보 저장소 | 회사·사용자·서버·권한 등의 원본 보관 | DynamoDB |
| 빠른 조회용 저장소 | 요청마다 확인할 권한 정보, 호출 제한, 로그 전달 | Redis |
| 파일 저장소 | 분석 결과, 차트, 보고서, 내보낸 파일 보관 | S3 호환 저장소 |

관리 정보의 원본은 DynamoDB에 둔다. MCP 요청마다 필요한 권한 정보는 Redis에 복사해 사용한다. 두 저장소 사이의 반영이 누락되면 다시 처리하고, 주기적으로 차이를 점검해 복구하는 코드도 들어 있다.

## 4. 어떤 서버를 연결했나

| 서버 | 용도 | 제공하는 작업 | 회사별 범위 구분 |
| --- | --- | --- | --- |
| PostgreSQL | 일반 업무 데이터 | 테이블 조회, SQL 조회, 권한에 따른 추가·수정·삭제 | 스키마 또는 데이터베이스 |
| ClickHouse | 로그·분석 데이터 | 테이블 조회, SQL 조회, 집계 | 데이터베이스 또는 회사 구분 컬럼 |
| MongoDB | 문서 형태의 데이터 | 컬렉션 조회, 검색, 집계, 권한에 따른 추가·수정·삭제 | 데이터베이스 |
| Hacker | 버그바운티 데이터 | PostgreSQL 기반 읽기 전용 조회 | 스키마 또는 데이터베이스 |
| Ethie | 보안 점검 도구 | 탐색·취약점 점검·명령 및 코드 실행 요청 전달 | 프로그램 범위를 외부 실행 서버에 전달 |

고객사가 추가될 때마다 MCP 서버를 새로 개발하는 방식은 아니다. 기존 서버에 연결 정보를 등록하고, 그 회사가 사용할 데이터 범위를 설정한다. 샘플 DB에 있는 테이블 이름을 전제로 하지 않도록 구성했다.

Hacker와 Ethie는 역할이 다르다. Hacker는 이미 저장된 버그바운티 데이터를 읽고, Ethie는 점검 도구를 실행하는 외부 서버와 연결한다. Ethie 자체에는 점검 프로그램이 들어 있지 않으며, 실제 실행과 대상 범위 통제는 연결된 실행 서버에서도 처리해야 한다.

## 5. 권한은 어떻게 나누나

권한의 기준은 **회사 → 사용자 → 서버 접근**이다. API 키는 사용자를 대신해 요청할 때 쓰며, 사용자가 가진 권한보다 더 큰 권한을 가질 수 없다.

| 항목 | 의미 | 예시 |
| --- | --- | --- |
| 회사 | 데이터와 사용자를 나누는 단위 | A 고객사 |
| 사용자 | 실제로 서비스를 사용하는 사람 | A사 보안 담당자 |
| 서버 | 연결할 데이터나 도구 | 제보 DB, 분석 DB, Ethie |
| 회사별 연결 설정 | 해당 회사가 서버에서 사용할 범위 | A사 전용 스키마 |
| 서버 접근 권한 | 사용자가 특정 서버에서 할 수 있는 일 | 조회만 허용, 조회와 내보내기 허용 |
| 허용 도구 | 권한 안에서 사용할 도구를 더 좁힌 목록 | 조회 도구 중 일부만 허용 |
| API 키 범위 | 그 키로 접근할 수 있는 서버 | 분석 DB에만 사용할 키 |

예를 들어 담당자가 제보 DB와 분석 DB에 접근할 수 있어도, API 키를 분석 DB 전용으로 발급하면 그 키로는 제보 DB에 접근할 수 없다.

| 권한 | 허용하는 작업 | 적용 예 |
| --- | --- | --- |
| `read` | 조회, 정리, 분석, 차트 미리보기, 모니터 관리 | 데이터 조회와 통계 확인 |
| `create` | 데이터 추가 | PostgreSQL 행 추가, MongoDB 문서 추가 |
| `update` | 데이터 수정 | 기존 데이터 변경 |
| `delete` | 데이터 삭제 | 행 또는 문서 삭제 |
| `export` | 파일 내보내기, 산출물 저장, 보고서 생성 | Excel 다운로드, 분석 결과 저장 |
| `execute` | Ethie 도구 실행 | 외부 보안 점검 도구 호출 |

조회할 수 있다고 파일 저장까지 허용되는 것은 아니다. 분석 결과나 차트를 저장하는 작업에도 `export` 권한을 확인한다. 여러 서버의 결과를 보고서로 합칠 때는 원본이 나온 서버들의 권한도 다시 확인한다.

## 6. 회사 데이터가 섞이지 않도록 한 부분

### 멀티테넌트 구현 방식

이 프로젝트에서 테넌트는 회사다. A사와 B사가 같은 MCP 서버에 접속하더라도, API 키에 연결된 회사 정보를 기준으로 서로 다른 데이터 범위를 사용한다. 회사마다 별도 MCP 컨테이너를 띄우는 방식이 아니라, 공통 서버 안에서 인증·권한·데이터 접근 범위를 나누는 구조다.

데이터를 나누는 방식은 연결한 DB에 맞춰 선택한다. 모든 DB에서 같은 방식의 격리를 제공하는 것은 아니다.

| 격리 방식 | 어떻게 나누나 | 지원 서버 | 설정 예시 |
| --- | --- | --- | --- |
| 스키마 분리 | 하나의 DB 안에서 회사마다 다른 스키마 사용 | PostgreSQL, Hacker | A사는 `acme`, B사는 `globex` |
| 데이터베이스 분리 | 회사마다 다른 DB 사용 | PostgreSQL, Hacker, ClickHouse, MongoDB | A사는 `acme_db`, B사는 `globex_db` |
| 행 단위 분리 | 같은 테이블에서 회사 구분 컬럼의 값으로 행 제한 | ClickHouse | A사는 `company_id = 'acme'`인 행만 조회 |

PostgreSQL과 Hacker의 컬럼 기반 행 단위 격리는 현재 지원하지 않는다. MongoDB도 현재는 DB 분리 방식만 지원한다. 지원하지 않는 방식을 등록하면 설정 단계에서 거부한다.

이 격리는 MCP를 통한 접근에 적용된다. DB 자체의 Row-Level Security 정책을 자동으로 만드는 방식은 아니다. 회사별 DB 계정을 별도로 지정하는 기능도 있지만 필수 설정은 아니므로, DB 계정 자체의 접근 범위는 실제 연결 설정에 따라 달라진다.

### DB 사용자 계정도 따로 사용할 수 있나

**PostgreSQL·ClickHouse·MongoDB 모두 회사별 DB 사용자명과 비밀번호로 접속하는 기능이 구현되어 있다.** 관리 콘솔에서 회사에 서버 바인딩을 추가할 때 전용 접속 계정을 입력할 수 있다. 입력한 계정은 해당 회사와 서버의 연결 설정에 저장된다.

| DB | 전용 계정을 설정했을 때 | 적용 코드 |
| --- | --- | --- |
| PostgreSQL·Hacker | 기본 접속 주소의 사용자명·비밀번호를 회사 전용 계정으로 교체하고, 지정한 DB 또는 스키마 사용 | `libs/common/mcpcluster_common/postgres/pool.py`의 `dsn_for` |
| ClickHouse | 클라이언트 생성 시 회사 전용 `username`·`password` 적용 | `mcp-clickhouse/mcp_clickhouse/client.py`의 `_make_client` |
| MongoDB | 접속 URI의 사용자명·비밀번호 교체. 인증 DB인 `authSource`는 회사에 지정된 DB로 설정 | `mcp-mongo/mcp_mongo/client.py`의 `connect_args` |

계정 선택의 우선순위는 **회사별 전용 계정 → 등록된 서버 접속 정보의 계정 → 서버 기본 환경 설정의 계정**이다. 회사별 전용 계정을 입력하지 않으면 공통 계정으로 연결하고, 앞서 설명한 스키마·DB·쿼리 조건으로 데이터 범위를 나눈다.

예를 들어 A사와 B사가 같은 PostgreSQL 서버를 사용하더라도, A사 바인딩에 `acme_reader`, B사 바인딩에 `globex_reader`를 등록하면 실제 DB 연결도 각 계정으로 이루어진다. DB에서 각 계정의 접근 권한을 따로 설정해 두면, MCP의 접근 검사에 더해 DB 자체 권한도 적용된다.

| 구분 | 현재 구현 |
| --- | --- |
| 회사별 DB 계정 입력 | 관리 콘솔과 API에서 지원 |
| 비밀번호 저장 | 암호화하여 저장하고, 연결할 때 복호화 |
| 실제 DB 접속에 계정 적용 | 지원 |
| 회사별 연결 재사용 | 회사 ID와 서버 ID별로 연결 관리 |
| 계정 변경 반영 | 바인딩 버전 변경 후 연결을 다시 생성할 때 적용 |
| 회사별 전용 DB 계정 필수 사용 | 강제하지 않음. 선택 사항 |
| DB 계정 생성과 권한 부여 | 바인딩 등록이 `CREATE USER`나 `GRANT`를 자동 수행하지 않음. DB 쪽에서 준비 필요 |
| 서비스 사용자마다 다른 DB 계정 사용 | 같은 회사·서버 바인딩 안에서 사용자별로 DB 계정을 바꾸는 구조는 아님 |

즉, **회사·서버별 DB 계정 분리는 지원하지만, 서비스 사용자와 DB 사용자가 일대일로 대응하지는 않는다.** 같은 회사에서 같은 서버를 쓰는 사람들은 바인딩의 DB 계정을 공유하고, 개인별 조회·수정·내보내기 권한은 MCP의 `ServerAccess`에서 구분한다. 같은 회사가 서로 다른 DB 계정으로 연결해야 한다면 별도의 서버 등록과 바인딩으로 구분할 수 있다.

MongoDB의 전용 계정은 현재 회사에 지정한 DB에서 인증하도록 되어 있다. 다른 인증 DB, 예를 들어 `admin`을 전용 계정 설정에서 따로 고르는 기능은 없다.

### 회사별 데이터 범위 설정 예시

`TenantBinding`은 “이 회사가 이 서버에서 어느 데이터를 사용하는가”를 저장하는 설정이다. 회사와 서버의 조합마다 하나씩 둔다.

| 회사 | 연결 서버 | 회사별 연결 설정 예시 | 접근하는 데이터 |
| --- | --- | --- | --- |
| A사 | 공용 PostgreSQL 서버 | `mode: schema`, `schema_name: acme` | `acme` 스키마의 테이블 |
| B사 | 공용 PostgreSQL 서버 | `mode: schema`, `schema_name: globex` | `globex` 스키마의 테이블 |
| A사 | 공용 ClickHouse 서버 | `mode: column`, `column: company_id`, `value: acme` | 회사 구분값이 `acme`인 행 |
| B사 | 공용 ClickHouse 서버 | `mode: column`, `column: company_id`, `value: globex` | 회사 구분값이 `globex`인 행 |
| A사 | 공용 MongoDB 서버 | `mode: database`, `database: acme_db` | `acme_db`의 컬렉션 |

위 이름은 설명용 예시다. 실제 값은 관리 콘솔에서 설정한다. 회사별 분리는 이 설정을 기준으로 하므로, 서로 다른 회사에 같은 스키마나 DB를 지정하면 데이터 범위도 같아진다. 회사 등록만으로 전용 DB나 스키마가 자동 생성되지는 않는다.

### 요청 하나가 처리되는 순서

| 순서 | 코드에서 하는 일 | 회사 격리와의 관계 |
| --- | --- | --- |
| 1. API 키 확인 | 키의 해시로 등록 정보를 조회하고 상태·만료 확인 | 키에서 `company_id`와 `user_id`를 확인 |
| 2. 대상 서버 확인 | 키 범위와 요청한 서버 확인 | URL의 서버 ID를 바꿔도 허용 범위를 벗어나면 거부 |
| 3. 접근 조건 확인 | 회사·사용자·서버·회사별 연결·사용자 접근이 모두 활성인지 검사 | 하나라도 없거나 정지 상태면 거부 |
| 4. 요청 전용 정보 생성 | `TenantContext`에 회사, 사용자, 서버, 데이터 범위, 권한 저장 | AI가 전달한 회사 이름 대신 인증된 설정 사용 |
| 5. 도구 권한 확인 | 호출 도구가 허용 목록과 작업 권한에 포함되는지 확인 | 같은 회사 안에서도 사용자별 작업 범위 제한 |
| 6. 회사별 연결 선택 | 회사 ID와 서버 ID를 기준으로 DB 연결 선택 | 다른 회사의 연결과 구분 |
| 7. 조회 범위 강제 | 서버 종류에 맞게 스키마·DB·행 조건 적용 | 실제 DB에 보내는 요청을 회사 범위로 제한 |
| 8. 요청 종료 | 요청에 묶인 회사 정보를 해제하고 접근 로그 기록 | 다음 요청에 이전 회사 정보가 남지 않도록 처리 |

`TenantContext`는 Python의 `ContextVar`로 관리한다. 여러 회사의 요청이 동시에 들어와도 각 실행 흐름이 자기 회사 정보를 참조한다. DB 연결은 `(company_id, server_id)`로 구분하며, 회사별 연결 설정이나 서버 접속 정보의 버전이 바뀌면 기존 연결을 닫고 다시 만든다.

### 같은 조회를 해도 회사마다 결과가 달라지는 이유

**PostgreSQL의 스키마 분리 예시**

A사와 B사가 모두 `SELECT name FROM customers`를 요청해도, 서버는 인증된 회사의 스키마를 쿼리에 명시한다. 아래 SQL은 동작을 설명하기 위해 단순화한 예시다.

| 호출한 회사 | AI가 요청한 SQL | 서버가 범위를 적용한 SQL |
| --- | --- | --- |
| A사 | `SELECT name FROM customers` | `SELECT name FROM acme.customers` |
| B사 | `SELECT name FROM customers` | `SELECT name FROM globex.customers` |

연결의 기본 스키마인 `search_path`도 고정하지만, 그것에만 의존하지 않는다. SQL을 파싱해 테이블 참조에 회사 스키마를 붙인다. A사 키로 `globex.customers`를 직접 지정하면 다른 회사 스키마 접근으로 거부한다. Hacker도 같은 공통 격리 코드를 사용하며, DB 연결 자체에 읽기 전용 설정을 추가한다.

**ClickHouse의 행 단위 분리 예시**

A사가 `SELECT kind, value FROM events`를 요청하면, 실제 테이블 참조를 다음과 같은 형태로 바꾼다.

```sql
SELECT kind, value
FROM (
    SELECT *
    FROM shared_db.events
    WHERE company_id = 'acme'
) AS events
```

맨 마지막에 회사 조건을 한 번 붙이는 방식이 아니라, 실제 테이블 참조마다 회사 조건으로 감싼다. JOIN이나 중첩 쿼리에서도 각 원본 테이블에 범위를 적용하기 위한 처리다. 회사 구분 컬럼이 없는 테이블은 목록에서 제외하고, 직접 조회해도 필요한 컬럼이 없어 실행되지 않는다.

**MongoDB의 DB 분리 예시**

도구가 사용할 DB를 `client[ctx.tenant.database]`로 선택한다. A사 키로 `customers`를 조회하면 `acme_db`의 컬렉션을 사용한다. 사용자가 도구 인자로 다른 DB를 선택하는 경로는 없으며, 서버 측 JavaScript나 다른 DB로 쓰기를 할 수 있는 파이프라인 연산도 제한한다.

### 조회 이후에도 적용되는 범위

| 영역 | 분리 방법 |
| --- | --- |
| 분석·차트·내보내기 | 원본 데이터를 가져올 때 같은 서버의 조회 가드와 회사별 연결 사용 |
| 저장된 산출물 | 회사·사용자별 경로에 저장하고, 읽을 때 메타데이터의 회사·소유 사용자와 무결성 확인 |
| 여러 서버를 합친 보고서 | 참조한 산출물의 소유권과 모든 원천 서버의 필요한 권한 재확인 |
| 모니터링 | 등록에 사용한 키를 기준으로 매 실행 재인증하고 회사 범위에서 조회 |
| 관리 API | 회사 관리자는 자기 회사만 접근 가능. 전체 회사 관리 권한은 `master`에 별도 부여 |
| Ethie | 인증된 회사와 프로그램 범위를 외부 실행 서버에 전달. 실제 점검 대상 범위 강제는 외부 실행 서버의 구현에도 의존 |

산출물은 같은 회사라는 이유만으로 모든 직원에게 공유되지 않는다. 현재 구현은 회사뿐 아니라 소유 사용자까지 확인한다.

### 구현을 확인한 코드와 테스트

| 파일 | 확인한 내용 |
| --- | --- |
| `backend/app/domain/tenant.py` | 서버별로 지원하는 격리 방식과 설정 검증 |
| `backend/app/services/bindings.py` | 회사와 서버의 연결 설정 저장·변경 |
| `libs/common/mcpcluster_common/authz.py` | API 키 → 회사·사용자 → 서버·연결·접근 권한 검사 |
| `libs/common/mcpcluster_common/middleware.py` | 호출마다 권한 검사, 요청별 회사 정보 설정·해제 |
| `libs/common/mcpcluster_common/connections.py` | 회사·서버별 연결 분리 및 설정 변경 시 재생성 |
| `libs/common/mcpcluster_common/postgres/sqlguard.py` | PostgreSQL 스키마 강제와 다른 스키마 접근 거부 |
| `mcp-clickhouse/mcp_clickhouse/sqlguard.py` | DB 범위 검사와 테이블별 회사 조건 주입 |
| `mcp-mongo/mcp_mongo/server.py` | 회사에 지정된 MongoDB 데이터베이스 선택 |
| `libs/common/mcpcluster_common/artifacts.py` | 저장 결과의 회사·사용자 소유권 검사 |

서버별 `tests/test_e2e.py`에는 A사와 B사의 키로 같은 조회를 실행해 서로 다른 결과를 확인하는 테스트가 있다. 다른 회사 스키마·DB 접근 거부, ClickHouse의 행 조건 적용, 회사·사용자 정지 후 접근 차단을 확인하는 테스트도 작성되어 있다.

여기서 확인한 것은 **멀티테넌트 실행 코드와 관련 테스트가 구현되어 있다는 사실**이다. 이번 문서 보완 과정에서 E2E 테스트를 다시 실행하거나, 운영 환경의 회사별 연결 설정까지 확인한 것은 아니다.

### 접근 단계별 보호 처리

다른 회사의 데이터에 접근하지 못하게 하는 처리는 AI의 지시 준수에 맡기지 않고 서버 코드에 넣었다.

| 확인 지점 | 구현한 처리 |
| --- | --- |
| 요청한 사용자 확인 | API 키와 연결된 회사·사용자 상태 확인 |
| 서버 접근 확인 | 키 범위, 사용자 권한, 허용 도구, 회사별 연결 상태 확인 |
| 권한 정보 누락 | 필요한 정보가 없으면 요청 거부 |
| 데이터 조회 | 설정된 스키마·DB·회사 구분 조건 안에서 실행 |
| 쿼리 검사 | SQL과 MongoDB 파이프라인 구조를 검사해 허용되지 않은 접근 제한 |
| 계정·키 정지 | 이후 요청에서 정지 상태를 확인해 차단 |
| 저장된 결과 조회 | 회사와 소유 사용자, 만료 여부, 무결성, 원천 서버 권한 재확인 |
| 민감 정보 처리 | 공통 데이터 처리 경로에서 이메일·전화번호·토큰 등 지정 패턴 마스킹 |
| 과도한 호출 제한 | API 키별 호출 횟수 제한 |
| 사용 이력 | 사용자·도구·실행 결과 등의 접근 로그 기록 경로 제공 |

마스킹은 설정에 따라 적용하며, 지정한 패턴을 바탕으로 동작한다. 모든 민감 정보를 자동으로 식별하는 기능은 아니다. API 키는 일반 키 저장 시 해시로 보관하고, DB 접속 정보는 암호화한다.

## 7. 분석 결과를 보고서까지 이어 쓰는 방식

분석할 때마다 나온 결과를 저장하고, 다음 작업에서는 그 결과의 ID를 참조한다. 코드에서는 이 저장된 결과를 `artifact`, 즉 산출물이라고 부른다.

| 단계 | 사용하는 도구 | 처리 내용 |
| --- | --- | --- |
| 정리 | `transform` | 열 선택, 형식 변환, 중복·빈 값 처리, 필터링 |
| 계산 | `compute` | 통계, 백분위, 상위 값, 상관관계, 이상치, 시간별 집계 |
| 시각화 | `chart` | 원본 조회 결과나 저장된 산출물로 차트 생성 |
| 저장 결과 확인 | `list_artifacts`, `get_artifact` | 내 산출물 목록과 내용 조회 |
| 데이터 파일 생성 | `export` | CSV·XLSX 생성 |
| 보고서 생성 | `report` | 여러 산출물을 PDF·DOCX·PPTX로 구성 |

예를 들어 PostgreSQL에서 조회한 업무 데이터와 ClickHouse에서 계산한 로그 통계를 각각 저장한 뒤, 한 보고서에 넣을 수 있다. 이때 서버끼리 직접 데이터를 주고받는 대신 공통 파일 저장소의 산출물을 참조한다.

계산에는 Rust 모듈을 사용하며, Rust 모듈이 없는 환경을 위한 Python 대체 구현도 있다. 두 구현의 결과가 같은지 비교하는 테스트가 마련되어 있다.

## 8. 모니터링은 어디까지 되나

조회 조건, 계산할 지표, 비교할 기준값, 실행 간격을 등록하면 서버가 주기적으로 실행한다. 예를 들어 “최근 한 시간의 오류 건수가 기준값을 넘었는지 5분마다 확인”하는 식이다.

| 항목 | 현재 동작 |
| --- | --- |
| 모니터 등록 | 조회 조건·계산 방식·기준값·주기 저장 |
| 주기 실행 | 서버 스케줄러에서 실행 |
| 권한 재확인 | 매 실행 시 생성에 사용한 키와 현재 접근 권한 확인 |
| 결과 확인 | 정상, 기준 초과, 실행 생략, 오류와 측정값 조회 |
| 관리 | 목록 조회, 일시정지, 재개, 삭제 |
| Slack·메일 알림 | 연결을 확장할 구조만 있으며, 현재 등록된 채널은 없음 |

현재는 AI에서 모니터 상태를 조회해 결과를 확인하는 방식이다. 기준값을 넘었다고 Slack이나 메일이 자동으로 발송되지는 않는다.

## 9. 관리자는 무엇을 설정하나

처음 사용하는 회사를 연결할 때는 다음 순서로 준비한다.

| 순서 | 관리 작업 | 설정하는 내용 |
| --- | --- | --- |
| 1 | 회사 등록 | 고객사 정보 |
| 2 | 사용자 등록 | 회사 소속 계정과 역할 |
| 3 | 서버 등록 | 서버 종류와 접속 정보 |
| 4 | 회사와 서버 연결 | 사용할 스키마·DB·회사 구분값 등 |
| 5 | 사용자 권한 부여 | 접근할 서버, 작업 권한, 허용 도구 |
| 6 | API 키 발급 | 사용할 서버 범위, 만료, 호출 제한 |
| 7 | AI 클라이언트 연결 | 게이트웨이 주소와 인증 설정 |

웹 콘솔에서는 회사·사용자·서버·연결 설정·접근 권한·키·로그를 관리한다. 회사별 보고서 표기와 색상 설정도 있다. 운영 화면에는 키가 실제로 사용 가능한지 확인하는 기능, 권한 정보 강제 동기화, Redis 정보 조회를 넣었다.

## 10. AI에서는 어떻게 연결하나

게이트웨이에 한 번 연결하면 그 키로 사용할 수 있는 서버들의 도구를 모아서 제공한다. 같은 이름의 도구를 구분하기 위해 `서버별칭__도구이름` 형식을 사용한다.

| 항목 | 구현 내용 |
| --- | --- |
| 공통 연결 주소 | 개발 환경 기준 `http://localhost:19000/mcp` |
| API 키 인증 | Bearer 헤더로 키 전달 |
| OAuth 연결 | 게이트웨이의 동의 화면에서 발급받은 API 키 입력 |
| 도구 구분 | 예: `sales-pg__run_select` |
| 공통 도구 | 보고서·산출물 조회 도구 일부는 하나로 제공 |
| 실제 권한 확인 | 요청을 받은 개별 MCP 서버에서 수행 |

저장소에는 Claude Code, Claude Desktop, OpenAI API, ChatGPT·Claude.ai 연결을 위한 가이드와 OAuth 구현이 있다. 외부 서비스에서 연결하려면 접근 가능한 서버 주소가 필요하고, 실제 사용 가능 여부는 해당 클라이언트의 MCP 지원과 설정에 따른다.

## 11. 현재 구현과 추가 연결이 필요한 부분

| 구분 | 코드 기준 상태 |
| --- | --- |
| 관리 콘솔과 관리 API | 구현됨 |
| 회사·사용자·서버별 권한 관리 | 구현됨 |
| 데이터 서버 4종과 공통 분석 도구 | 구현됨 |
| 파일 내보내기·차트·보고서 | 구현됨 |
| 게이트웨이와 OAuth 연결 | 구현됨 |
| 주기 모니터링과 결과 조회 | 구현됨 |
| Slack·메일 알림 | 알림 채널 구현·등록 필요 |
| Ethie 연결 | MCP 도구와 전달 코드 구현됨. 외부 실행 서버 연결 필요 |
| 실행·배포 구성 | Docker Compose와 인프라 설정 코드가 있음. 실제 운영 배포 여부는 별도 확인 필요 |

테스트는 백엔드·MCP 서버 테스트, 전체 연결 흐름 테스트, 관리 콘솔 브라우저 테스트, Rust와 Python 결과 비교로 나뉜다. 전체 흐름과 화면 테스트는 일회용 격리 환경을 띄워 실행하도록 구성되어 있다. 이 문서 작성 과정에서는 코드를 확인했으며, 테스트를 새로 실행하지는 않았다.
